# 서비스 분해

> 핵심 질문: 서비스 경계는 무엇을 기준으로 나누는가?

## Background Knowledge(배경지식)

01에서 지금 회사 시스템을 분산 모놀리스에 가깝다고 진단했다. 그때 기능 하나에 모든 서비스를 고쳐야 하는 이유가 서비스를 비즈니스 역량이 아니라 기술 역할 기준으로 나눴기 때문일 수 있다고 추정했다. 이번 주제에서 그 추정을 확인한다.

### Preliminary Questions(사전질문)

- 서비스 경계를 나누는 기준에는 무엇이 있는가?
- 잘못 나눈 경계는 어떤 모습으로 드러나는가?
- 지금 회사의 서비스 경계는 어떤 기준으로 나뉘어 있는가?

---

## Contents

### 1. 문제: 경계를 잘못 나누면 생기는 일

경계를 잘못 나누면 기능 하나를 바꿀 때 서비스 여러 개를 함께 고치고 함께 배포해야 한다. 서비스를 나눈 비용은 치르는데 독립 배포라는 이득은 얻지 못한다. 01의 분산 모놀리스가 바로 이 상태다.

### 2. 해법: 두 가지 분해 기준

| 기준 | 내용 | 예 |
|------|------|----|
| 비즈니스 역량(business capability) | 회사가 돈을 버는 데 필요한 활동 단위로 나눈다 | 주문 관리, 쿠폰 관리, 정산 |
| 하위 도메인(subdomain, DDD) | 도메인 모델과 용어가 일관된 범위(Bounded Context)로 나눈다 | 같은 "상품"도 카탈로그와 배송에서 뜻이 다르면 다른 컨텍스트 |

두 기준 모두 "무엇을 처리하는가"로 나누고 "어떻게 실행하는가"로 나누지 않는다.

판단에 쓰는 원칙은 **공통 폐쇄 원칙(Common Closure Principle, CCP)**이다. 같은 이유로 함께 바뀌는 것은 한 곳에 모으고 다른 이유로 바뀌는 것은 나눈다. 클래스 수준의 단일 책임 원칙을 서비스 수준으로 올린 것이다.

### 3. 분해 안티패턴

| 안티패턴 | 모습 | 왜 문제인가 |
|----------|------|-------------|
| 기술 계층 기준 | API 서비스, 배치 서비스, DB 서비스 | 도메인 규칙 하나가 여러 서비스에 흩어진다 |
| 작업 흐름 단계 기준 | 접수 서비스, 검증 서비스, 처리 서비스 | 요청 하나가 모든 서비스를 거친다 |
| 엔티티 기준 | 회원 CRUD 서비스, 상품 CRUD 서비스 | 로직 없는 데이터 접근 계층이 되고 규칙은 호출하는 쪽에 흩어진다 |
| 너무 잘게 나눔(nano-service) | 함수 하나가 서비스 하나 | 네트워크 비용과 운영 비용이 이득보다 크다 |

### 4. 트레이드오프

- 도메인 기준으로 나누면 규칙 변경은 한 곳에서 끝난다. 대신 도메인 사이 협력은 API나 이벤트 계약으로 해야 한다.
- 도메인 경계는 **모듈 경계**이지 곧바로 **서비스 수**가 아니다. 한 코드베이스 안에서 모듈로 먼저 나누고 독립 배포가 꼭 필요한 도메인만 서비스로 분리한다.
- 기존 경계를 바꾸기 전에 왜 그렇게 나눴는지부터 확인한다(체스터턴의 울타리). 예를 들어 API와 배치를 나눈 이유가 실행 환경(요청 응답 대 장시간 작업) 차이라면 도메인 모듈은 하나로 두고 실행 프로세스만 둘로 띄우는 방법도 있다.

## 현재 시스템 진단

### 서비스 구성

서비스는 API, 배치, 알림, CRM 등으로 나뉘어 있다(사용자 말). 코드를 보니 이 밖에도 파트너용 API·배치, 배송, 이미지 처리 등 서비스가 더 있었다.

| 서비스 | 분해 기준 | 판단 |
|--------|-----------|------|
| API / 배치 | 실행 방식(기술 계층) | 안티패턴. 같은 도메인이 두 서비스에 나뉜다 |
| 파트너 API / 파트너 배치 | 실행 방식(기술 계층) | 위와 같은 방식이 반복된다 |
| 알림 | 범용 하위 도메인 | 타당한 경계 |
| CRM | 비즈니스 역량 | 타당한 경계 |

### 근거: 같은 도메인 규칙이 두 서비스에 있다

쿠폰 발급 규칙(만료 검사, 중복 발급 정책, 최대 중복 수, 제한 수량 차감)이 API 서비스(회원 다운로드)와 배치 서비스(관리자 대량 지급)에 각각 구현돼 있다. 규칙 하나가 바뀌면 두 서비스를 모두 고쳐야 하므로 CCP 위반이다.

- 제한 수량의 기준 저장소(canonical)를 두 서비스가 다르게 적어 두었다. API는 DB를, 배치는 캐시(Redis)를 기준으로 삼고, 배치는 주기적으로 캐시 값으로 DB를 덮어쓴다.
- (추정) 두 경로가 동시에 돌면 서로 다른 값을 보고 수량을 판단해 초과 발급이나 잘못된 소진 판정이 생길 수 있다. 동기화 로직을 끝까지 읽지 않아 실제로 일어나는지는 확인하지 않았다.
- 배치 서비스가 정의한 테이블 모델 대부분(약 99%)을 API 서비스도 따로 정의하고 있다. 테이블 이름만 비교했고 컬럼까지 같은지는 보지 않았다.

### 도메인 기준으로 다시 묶는다면

핵심 도메인: **쿠폰, 주문, 정산, 상품, 회원** (사용자 답)

배치 코드의 폴더 구성을 보면 아래도 후보다.

- 판매자(파트너), 배송, 고객 문의(CS)
- (추정) 배치에는 도메인 규칙을 실행하는 작업과 분석용 ETL이 섞여 있다. 도메인 규칙을 실행하는 배치(예: 쿠폰 대량 지급)는 해당 도메인 모듈로 옮기고 분석 ETL은 "데이터 플랫폼"으로 따로 묶는 편이 자연스럽다. 배치 자체가 문제가 아니라 도메인 규칙이 배치 쪽에 흩어진 게 문제다.

### 쿠폰과 프로모션은 다른 도메인이다

프로모션과 쿠폰은 서로 다른 도메인으로 보고 따로 고도화한다(사용자 판단).

- 바뀌는 이유가 다르다. 프로모션은 언제, 누구에게, 무엇을 노출하고 혜택을 줄지 정하는 기획 단위다. 쿠폰은 발급, 수량, 중복, 사용 규칙을 가진 혜택 수단이다.
- 쿠폰은 프로모션 없이도 발급된다(관리자 대량 지급, 회원 다운로드). 그래서 "프로모션 아래 쿠폰"으로 두면 단독 쓰임새가 어색해진다.
- 관계는 "프로모션이 쿠폰을 혜택 수단으로 쓴다"이다.

지금 코드는 두 도메인이 서로의 규칙을 알고 있다.

- 프로모션 쪽 배치가 쿠폰 데이터를 직접 읽어 할인 금액(최소 금액, 할인 유형, 할인 값, 최대 할인)을 계산한다. 할인 계산은 쿠폰 도메인의 규칙이다.
- 쿠폰 쪽 코드에도 프로모션을 참조하는 곳이 있다. 어떻게 쓰는지는 읽지 않았다.
- (추정) 그래서 할인 규칙이 바뀌면 프로모션도 함께 고쳐야 하는 양방향 결합일 가능성이 크다.

### 협력 방식: 이벤트로 반응한다

두 도메인은 동기 호출 대신 이벤트를 발행하고 구독하는 방식으로 협력한다(사용자 판단). 도메인을 나눠 놓고 동기 호출로 다시 묶을 필요는 없다고 본다.

이 결정을 적용할 때 따져 볼 점(검토 의견):

- 이벤트는 "알리고 끝나는" 협력에 맞는다. 예: 프로모션이 시작되면 이벤트를 내고 쿠폰이 그것을 듣고 대상 회원에게 쿠폰을 발급한다.
- "답이 바로 필요한" 협력도 있다. 예: 프로모션 상품의 할인가를 노출하려면 할인 금액이 필요하다. 이때 이벤트만 쓰려면 쿠폰이 할인 정책이 바뀔 때마다 이벤트를 내고 프로모션이 그 사본을 들고 계산해야 한다(이벤트로 상태 전달). 사본은 잠시 어긋날 수 있고(최종 일관성), 계산 규칙을 사본 쪽에서 다시 구현하면 지금의 중복이 그대로 남는다.
- 두 도메인이 한 배포 단위 안의 모듈이라면 쿠폰 모듈의 공개 기능을 함수로 부르는 것은 네트워크 동기 호출이 아니다. 시간적 결합 문제가 생기지 않는다.
- 이벤트를 쓰더라도 의존 방향을 정해야 한다. 쿠폰이 프로모션 이벤트를 구독하면 쿠폰이 프로모션의 이벤트 형식을 알게 된다. 어느 쪽이 상대의 언어를 알아도 되는지 정한다.

## Study Reflection

### Answers to Preliminary Questions(사전 질문에 대한 답변)

- 경계는 비즈니스 역량이나 하위 도메인으로 나눈다. 판단 기준은 "같은 이유로 함께 바뀌는가"(CCP)와 "같은 말을 같은 뜻으로 쓰는가"(Bounded Context)다.
- 잘못 나눈 경계는 같은 도메인 규칙이 여러 서비스에 중복되는 모습으로 드러난다. 그래서 기능 하나에 여러 서비스를 함께 고치게 된다.
- 지금 회사는 API와 배치라는 실행 방식 기준으로 나뉘어 있다. 쿠폰 발급 규칙이 두 서비스에 각각 있고 수량의 기준 저장소도 서로 다르다.

### Evolving Thoughts

처음에는 서비스 구성 전체를 안티패턴으로 봤다. 하나씩 따져 보니 알림과 CRM은 타당한 경계였고 문제는 API와 배치의 분리였다. 그것도 배치 자체가 아니라 도메인 규칙이 실행 방식에 따라 흩어진 것이 문제였다.

도메인을 나누는 일과 협력 방식을 고르는 일은 따로다. 나눈 뒤에도 "결과를 바로 알아야 하는가"에 따라 이벤트와 직접 호출을 골라야 한다. 이건 03 통신과 04 데이터 관리에서 이어서 본다.
