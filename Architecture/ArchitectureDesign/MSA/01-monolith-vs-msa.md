# 모놀리스와 MSA

> 핵심 질문: MSA는 언제 쓰고, 언제 쓰지 말아야 하는가?

## Background Knowledge(배경지식)

지금 다니는 회사의 시스템은 MSA다. 서비스는 목적과 역할에 따라 나뉘어 있지만 동작이 완전히 분리되어 있지 않다. MSA에서 흔히 쓰는 패턴 대신 자체적으로 설계한 구조를 쓰고 있어서 아직 미숙한 MSA로 보인다.

### Preliminary Questions(사전질문)

- 모놀리스의 어떤 문제 때문에 MSA를 쓰는가?
- MSA로 얻는 것과 그 대가는 무엇인가?
- 지금 회사의 MSA는 어떤 상태이고 성숙한 MSA로 가려면 무엇을 알아야 하는가?

목표: 성숙해 가는 MSA를 설계할 수 있는 지식을 쌓고 실제 업무에 적용한다.

## Contents

### 1. 모놀리스가 문제가 되는 시점

모놀리스는 하나의 코드베이스를 하나의 단위로 빌드하고 배포하는 구조다. 처음부터 나쁜 구조는 아니다.

- 함수 호출은 네트워크를 거치지 않아서 빠르고 실패하지 않는다.
- 트랜잭션 하나로 데이터 정합성을 보장할 수 있다.
- 배포하고 모니터링하고 디버깅할 대상이 하나뿐이다.

문제는 시스템과 조직이 커질 때 생긴다. Richardson은 이 상태를 "monolithic hell"이라고 부른다.

| 증상 | 원인 | MSA 없이 해결할 수 있는가 |
|------|------|------|
| 작은 수정에도 전체를 다시 배포한다 | 배포 단위가 하나다 | 없다 |
| 팀끼리 서로 기다린다 | 같은 코드베이스와 릴리스 일정을 공유한다 | 일부 가능 |
| 일부 기능만 확장할 수 없다 | 기능들이 한 프로세스에 묶여 있다 | 없다 |
| 기술 스택을 바꾸기 어렵다 | 전체를 한 번에 바꿔야 한다 | 없다 |
| 코드가 점점 얽힌다 | 모듈 경계를 강제하는 장치가 없다 | **있다** (모듈러 모놀리스) |

대부분은 기술 문제가 아니라 조직 문제다. 팀 하나가 다루는 시스템에서는 이런 증상이 잘 나타나지 않는다.

### 2. 모듈러 모놀리스

배포 단위는 하나로 두고 내부를 기능과 목적에 따라 모듈로 나눈다. 모듈 경계를 명확히 하고 단일 책임 원칙을 지키면 결합이 느슨해진다.

원칙만으로는 경계가 지켜지지 않는다. 마감에 쫓기면 다른 모듈의 내부 클래스를 직접 부르게 되므로, 경계를 도구로 강제해야 한다.

- 빌드 모듈 분리(Gradle 멀티 모듈): 의존을 선언하지 않은 모듈은 참조할 수 없다.
- 아키텍처 테스트(ArchUnit 등): 패키지 간 참조 규칙을 테스트로 검사한다.
- 공개 API 패키지만 노출하고 내부 구현은 숨긴다.

모듈러 모놀리스로 풀 수 없는 것은 **배포 단위가 하나라는 문제**다. MSA를 검토할 이유는 여기서 생긴다.

### 3. MSA로 얻는 것과 대가

| 얻는 것 | 대가 |
|---------|------|
| 서비스별 독립 배포 | 서비스 사이 API 계약을 관리해야 한다(버전, 하위 호환) |
| 팀 자율성 | 경계를 잘못 나누면 팀 간 조율이 오히려 늘어난다 |
| 서비스별 확장 | 네트워크 호출은 느리고 실패할 수 있다 |
| 장애 격리 | 격리 장치(타임아웃, 서킷 브레이커)가 없으면 장애가 퍼진다 |
| 서비스별 DB와 기술 선택 | 트랜잭션 하나로 정합성을 맞출 수 없다(Saga, 이벤트 필요) |
| | 분산 추적, 로그 수집, 배포 파이프라인 같은 운영 비용 |

Martin Fowler는 이 대가를 "Microservice Premium"이라고 부른다. 시스템이 단순할 때는 비용이 이득보다 크기 때문에 모놀리스로 시작하라고 권한다("MonolithFirst").

왼쪽 열은 오른쪽 대가를 치렀을 때만 얻을 수 있다.

### 4. 분산 모놀리스

서비스는 물리적으로 나뉘어 있지만 강하게 결합돼 있어서 사실상 하나처럼 움직이는 상태다. 모놀리스와 MSA의 단점을 함께 가진다. 대가는 치르는데 이득은 얻지 못한다.

판별 기준:

- 서비스 A를 배포할 때 B, C도 같이 배포해야 한다.
- 요청 하나가 서비스 여러 개를 동기 호출로 줄줄이 거친다.
- 서비스 둘 이상이 같은 DB 테이블을 직접 읽거나 쓴다.
- 서비스 하나가 죽으면 관련 없는 기능까지 멈춘다.
- 공통 라이브러리를 바꾸면 모든 서비스를 다시 배포해야 한다.

### 5. 비동기여도 결합될 수 있다

통신 방식이 비동기라고 결합이 느슨해지지는 않는다. 이벤트를 보낸 쪽이 콜백을 받을 때까지 기능을 "미완료"로 두면 사실상 동기 호출과 같다. 상대가 살아 있어야 내 기능이 끝나기 때문이다. 이를 **시간적 결합(temporal coupling)**이라고 한다.

제대로 분리된 비동기 구조에서는 소비자가 죽어도 메시지가 큐에 쌓여 있다가, 소비자가 살아나면 처리된다. 처리가 늦어질 뿐 실패하지는 않는다.

콜백(응답 메시지)이 항상 불필요한 것은 아니다. 따져야 할 질문은 두 가지다.

- 이 단계의 결과를 호출한 쪽이 꼭 알아야 하는가?
  - 알림, 통계, 검색 색인처럼 몰라도 되는 처리는 이벤트만 보내면 된다(fire-and-forget).
  - 결제처럼 결과에 따라 다음 단계가 바뀌는 처리는 응답이 필요하다(Saga 오케스트레이션).
- 꼭 알아야 한다면, 상대가 죽었을 때 기능을 실패로 처리할 것인가, 기다릴 것인가?

### 6. 최종 일관성에 필요한 것

서비스 사이 데이터가 결국 맞아떨어지려면 네 가지가 모두 필요하다.

1. 원자적 발행: DB 저장과 이벤트 발행을 묶는다(Transactional Outbox).
2. 최소 한 번 전달과 재시도(at-least-once, DLQ)
3. 멱등한 소비자: 같은 메시지를 두 번 받아도 결과가 같다.
4. 비즈니스 실패에 대한 보상(Saga의 보상 트랜잭션)

아웃박스의 목적은 "DB 저장과 이벤트 발행이 둘 다 일어나거나 둘 다 안 일어나게" 하는 것이다. 비즈니스 데이터와 이벤트 레코드를 같은 트랜잭션으로 저장하고 별도 릴레이가 아웃박스 테이블을 읽어 브로커로 발행한다. 이렇게 하지 않으면 DB 커밋은 됐는데 이벤트 발행은 실패하는 일이 생겨 서비스 간 데이터가 계속 어긋날 수 있다.

읽기와 쓰기를 나누는 것(CQRS의 일부)과 서비스마다 DB를 나누는 것(Database per Service)은 다른 이야기다.

## 현재 시스템 진단

분산 모놀리스 판별 기준 5개 중 4개에 해당한다.

| 기준 | 해당 여부 | 내용 |
|------|-----------|------|
| 같이 배포 | 해당 | 기능 하나를 배포하려면 나뉜 서비스를 모두 개발해야 한다 |
| 동기 호출 체인 | 비해당 | 비동기 이벤트로 통신한다. 다만 콜백으로 완료를 확인한다 |
| DB 공유 | 해당 | DB 하나를 공유한다. 읽기와 쓰기만 나뉘어 있다 |
| 장애 전파 | 해당 | 서비스 하나가 고장 나면 기능이 올바르게 완료되지 않는다. 가장 큰 문제다 |
| 공통 라이브러리 | 해당 | |

- 아웃박스는 있지만 로깅 용도로만 쓴다고 들었다. 최종 일관성이 보장되지 않는 것으로 보인다.
- (추정) 기능 하나에 모든 서비스를 고쳐야 하는 건, 서비스를 비즈니스 역량이 아니라 처리 단계나 기술 역할 기준으로 나눴기 때문일 수 있다. 02에서 확인한다.
- (추정) 장애가 전파되는 건 콜백을 기다리는 시간적 결합 때문일 수 있다. 재시도나 DLQ가 없는 것도 원인일 수 있다.

### 방향: 모놀리스로 되돌릴 것인가, MSA를 성숙시킬 것인가

지금 단계에서는 **MSA를 성숙시키는 쪽(B)**이 맞다고 본다.

- 서비스를 완전히 이해하지는 못했지만 아직 개선할 수 있는 수준으로 보인다.
- 다만 서비스가 급성장하고 있어서 개선에 시간을 투자해 해결할 수 있는 문제인지 확인이 필요하다.

## Study Reflection

### Answers to Preliminary Questions(사전 질문에 대한 답변)

- 모놀리스의 문제 대부분은 조직이 커질 때 생긴다. 코드가 얽히는 문제는 모듈러 모놀리스로 풀 수 있고 MSA가 필요한 이유는 배포 단위가 하나라는 문제다.
- MSA는 독립 배포, 팀 자율성, 확장, 장애 격리를 주지만 그 대가로 분산 시스템의 복잡도를 치러야 한다. 대가만 치르고 이득을 못 얻으면 분산 모놀리스가 된다.
- 지금 회사는 분산 모놀리스에 가깝다. 서비스 분해, 데이터 관리, Outbox와 전달 보장, Saga를 알아야 한다.

### Evolving Thoughts

비동기로 통신하면 결합이 느슨하다고 생각하기 쉽지만 결과를 기다리는 순간 동기와 다르지 않다. 콜백을 없앨지가 아니라 "결과를 꼭 알아야 하는가"를 먼저 따져야 한다.
