# 리스크 주도 모델 (Risk-Driven Model)

리스크 주도 모델은 "아키텍처를 얼마나 해야 하는가?"라는 질문에 답하는 핵심 프레임워크이다.

> **핵심 원칙**: 아키텍처 작업의 양은 실패 리스크에 비례해야 한다.
> "Architecture efforts should be commensurate with the risk of failure"

**적용 범위**: 이 모델은 전체 개발 프로세스를 대체하지 않는다. **아키텍처 설계 단계에만** 적용되며, 애자일/워터폴 등 어떤 개발 방법론 내에서도 함께 사용할 수 있다.

<br>

## 3단계 프로세스

```
1. 리스크 식별 및 우선순위화
        ↓
2. 기법 선택 및 적용
        ↓
3. 리스크 감소 평가
        ↓
   (아직 리스크가 있으면 반복)
```

### 1단계: 리스크 식별 및 우선순위화 (Identify and Prioritize Risks)
프로젝트에서 실패를 야기할 수 있는 요인들을 찾아 우선순위를 정한다.

**리스크 공식**:
> **리스크 = 실패 확률(인식) × 실패 영향도(인식)**

- 실제 확률이 0이더라도 **불확실성(uncertainty)**이 있으면 리스크로 인식된다.
- 기법(technique)은 분석과 검증을 통해 불확실성을 줄임으로써 리스크를 낮춘다.

### 2단계: 기법 선택 및 적용 (Select and Apply Techniques)
식별된 리스크를 완화하기 위한 아키텍처 기법을 선택하고 적용한다.

**기법-리스크 매핑 예시**:
| 리스크 | 적합한 기법 |
|--------|------------|
| 성능 리스크 | 큐잉 이론(Queuing Theory), 성능 모델 |
| 보안 리스크 | 위협 모델링(Threat Modeling) |
| 신뢰성 리스크 | 단조 비율 분석(Rate Monotonic Analysis) |
| 확장성 리스크 | 로드 테스트, 용량 계획 |
| 통합 리스크 | 프로토타입, 스파이크 |

### 3단계: 리스크 감소 평가 (Evaluate Risk Reduction)
아키텍처 작업 후 남은 리스크가 수용 가능한 수준인지 평가한다.
- "이 아키텍처로 실패 리스크를 극복할 수 있는가?"
- 도메인 경험과 이해관계자 관점이 필요하다.
- 과소 설계(무시된 리스크)와 과잉 설계(낮은 영향의 완벽화) 모두 방지한다.

<br>

## 리스크의 분류

### 엔지니어링 리스크 (Engineering Risks)
기술적 문제 - 아키텍처 설계 기법으로 해결
- 성능, 확장성, 보안, 신뢰성
- 동시성, 데이터 일관성
- 시스템 통합, 외부 의존성

### 프로젝트 관리 리스크 (Project Management Risks)
일정, 팀 커뮤니케이션, 인력 문제 - **이 책의 범위 밖**
- 아키텍처가 아닌 관리 방식으로 해결

### 도메인별 프로토타입 리스크
| 도메인 | 주요 리스크 |
|--------|------------|
| IT 프로젝트 | 통합 복잡도, 불명확한 요구사항, 도메인 지식 부족 |
| 시스템 프로젝트 | 성능, 신뢰성, 동시성, 보안 |
| 웹 애플리케이션 | 보안 취약점, 확장성 |

<br>

## 문제 유형: 찾는 문제 vs 증명하는 문제

### 찾는 문제 (Problems to Find)
구체적이고 테스트 가능한 해결책이 있다.
- 예: "데이터베이스가 100자 이상의 이름을 저장할 수 있는가?"
- 간단한 테스트로 성공/실패 확인 가능

### 증명하는 문제 (Problems to Prove)
모든 경우에 대해 올바름을 보여야 한다.
- 예: "시스템이 항상 프레임워크 API에 부합하는가?"
- 광범위한 테스트로도 엣지 케이스 배제 불가
- 형식 검증(formal verification)이나 구조적 접근 필요

<br>

## 모델 유형: 유추적 vs 분석적

### 유추적 모델 (Analogic Models)
요소들이 실제 세계의 대응물에 직접 매핑된다.
- 인간의 추론으로 통찰을 도출
- 예: UML 다이어그램, 아키텍처 스케치

### 분석적 모델 (Analytic Models)
계산적 분석을 지원한다.
- 예: 큐잉 이론 모델 → 응답 시간 정량적 예측 가능
- 더 높은 정밀도와 객관성 제공

<br>

## 의도적으로 불완전한 아키텍처

리스크 주도 모델은 **의도적으로 불완전한** 아키텍처를 생산한다.
- 리스크가 식별된 영역만 상세히 설계한다.
- 예: 성능 문제는 있고 보안 문제가 없는 프로젝트 → 성능 모델만 개발, 보안 아키텍처는 생략

**모델은 목적이 아닌 수단이다**: 중간 산출물(intermediate product)이지, 그 자체가 최종 목표가 아니다.

<br>

## 언제 아키텍처를 멈출 것인가

**멈춤 조건**: 기술적 실패 리스크가 비기술적 리스크보다 낮아질 때까지

> "do enough architecture until the risk of technical failure is lower than non-technical risks"

**비기술적 리스크의 예**:
- 시장 출시 타이밍(time to market) 지연
- 잘못된 제품을 개발하는 리스크(risk of building the wrong thing)

| 상황 | 판단 |
|------|------|
| 기술적 실패 리스크 < 비기술적 리스크 | 아키텍처 작업 중단 가능 |
| 아직 기술적 위협 리스크가 큼 | 계속 반복 |
| 리스크가 낮은 영역을 완벽화하고 있음 | 과잉 설계, 중단 필요 |

<br>

## 기존 접근법과의 비교

| 접근법 | 문제점 |
|--------|--------|
| **설계 없음(No Design)** | 실패 리스크가 클 때 부적합 |
| **정해진 비율(Prescribed %)** | 맥락을 고려하지 않음 |
| **문서 템플릿** | 실제 리스크와 미정렬됨 |
| **임기응변(Ad hoc)** | 주관적, 조직적 학습 없음 |
| **리스크 주도 모델** | 리스크에 비례하는 적절한 설계 투자 |

<br>

## 3계층 시스템 적용 예시

```
[인터넷 노출 프론트엔드] ← 보안, 사용성 리스크 → 보안 아키텍처 집중
         ↓
[방화벽 내부 백엔드]    ← 처리량, 확장성 리스크 → 성능 모델링 집중
         ↓
[데이터 계층]           ← 일관성 리스크 → 데이터 아키텍처 집중
```

각 계층의 리스크가 다르므로, 아키텍처 작업도 계층마다 다르게 투자한다.
