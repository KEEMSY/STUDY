# 아키텍처 뷰타입과 모델

소프트웨어 아키텍처를 표현하려면 **다양한 관점**이 필요하다. 하나의 다이어그램으로 모든 것을 표현할 수 없다.

<br>

## 모델, 뷰, 뷰타입의 관계

```
모델(Model)
  └─ 시스템의 특정 측면을 추상화한 표현
       ↓
뷰(View)
  └─ 모델의 선택적 세부사항을 보여주는 표현
       ↓
뷰타입(Viewtype)
  └─ 관련 뷰들을 묶는 카테고리 (관련 뷰들의 어휘와 규칙 정의)
```

**핵심**: 같은 시스템도 보는 관점(뷰타입)에 따라 다른 모습으로 표현된다.

<br>

## 세 가지 뷰타입

### 1. 모듈 뷰타입 (Module Viewtype)
시스템의 **정적 구조** - 소스 코드 수준의 설계 단위

**표현 대상**: 클래스, 패키지, 모듈, 인터페이스, 상속 관계, 의존성

**분석에 적합한 품질 속성**:
- **수정 용이성(Modifiability)**: 변경의 영향 범위 파악
- **구현 관심사**: 모듈 분리, 계층화, 의존성 관리

**대표 다이어그램**: UML 클래스 다이어그램, 패키지 다이어그램, 계층 다이어그램

**예시 질문**: "이 기능을 변경할 때 몇 개의 모듈이 영향을 받는가?"

---

### 2. 런타임 뷰타입 (Runtime Viewtype)
시스템의 **동적 동작** - 실행 시점의 구조

**표현 대상**: 객체, 프로세스, 스레드, 메시지, 컴포넌트, 커넥터, 포트

**분석에 적합한 품질 속성**:
- **성능(Performance)**: 응답 시간, 처리량
- **동시성(Concurrency)**: 경쟁 조건, 교착 상태
- **가용성(Availability)**: 장애 전파 경로

**대표 다이어그램**: UML 시퀀스 다이어그램, 컴포넌트-커넥터 다이어그램, 상태 다이어그램

**예시 질문**: "이 요청이 처리되는 동안 어떤 프로세스들이 상호작용하는가?"

---

### 3. 할당 뷰타입 (Allocation Viewtype)
소프트웨어를 **환경(하드웨어/인프라)에 매핑** - 배포 구조

**표현 대상**: 서버, 네트워크, 클라우드 리전, 배포 단위, 파일 시스템

**분석에 적합한 품질 속성**:
- **보안(Security)**: 신뢰 경계, 네트워크 격리
- **신뢰성(Reliability)**: 단일 장애점, 이중화
- **인프라 관심사**: 비용, 지연시간, 물리적 제약

**대표 다이어그램**: 배포 다이어그램, 인프라 다이어그램, 네트워크 토폴로지

**예시 질문**: "이 서비스는 어느 서버에서 실행되고, 어떤 네트워크 경계를 넘는가?"

<br>

## 뷰타입과 품질 속성 매핑

| 품질 속성 | 가장 적합한 뷰타입 |
|-----------|------------------|
| 수정 용이성 | 모듈 뷰타입 |
| 성능 | 런타임 뷰타입 |
| 동시성 | 런타임 뷰타입 |
| 보안 | 할당 뷰타입 + 런타임 뷰타입 |
| 신뢰성 | 할당 뷰타입 |
| 테스트 용이성 | 모듈 뷰타입 |
| 배포 용이성 | 할당 뷰타입 |

<br>

## 세 가지 모델 유형

### 도메인 모델 (Domain Model)
실제 세계의 엔티티와 관계를 표현한다.
- 비즈니스 개념, 도메인 객체, 유비쿼터스 언어
- 구현과 독립적인 문제 영역(problem space) 표현

### 설계 모델 (Design Model)
소프트웨어 아키텍처 자체를 표현한다.
- 컴포넌트, 인터페이스, 의존성, 프로토콜
- 해결 공간(solution space) 표현

### 코드 모델 (Code Model)
실제 소스 코드 구현을 표현한다.
- 클래스, 메서드, 데이터 구조
- 설계 모델의 구체화

<br>

## 보조 모델 유형

| 모델 | 설명 |
|------|------|
| **개념 모델(Conceptual Model)** | 고수준 시스템 개요, 비기술 이해관계자용 |
| **시스템 컨텍스트 다이어그램** | 시스템과 외부 엔티티의 경계와 상호작용 |
| **데이터 흐름 다이어그램** | 데이터가 시스템을 통해 이동하는 경로 |

<br>

## 실용적 적용 가이드

### 리스크에 따른 뷰 선택
```
리스크: 성능 병목 우려
  → 런타임 뷰타입으로 컴포넌트 간 메시지 흐름 모델링
  → 큐잉 이론으로 분석

리스크: 보안 취약점 우려
  → 할당 뷰타입으로 신뢰 경계 확인
  → 위협 모델링 적용

리스크: 유지보수성 저하 우려
  → 모듈 뷰타입으로 의존성 파악
  → 변경 영향 분석
```

### 의도적으로 불완전한 뷰
모든 뷰를 만들 필요는 없다. **리스크가 있는 영역의 뷰만** 만들면 된다.

- 성능 리스크만 있다면 → 런타임 뷰만
- 배포 리스크만 있다면 → 할당 뷰만
- 여러 리스크가 있다면 → 해당 뷰들만

<br>

## C4 모델과의 관계

Simon Brown의 C4 모델(Context, Container, Component, Code)은 이 책의 뷰타입 개념에서 영향을 받았다.

| C4 레벨 | 대응하는 뷰타입 |
|---------|----------------|
| Context | 시스템 컨텍스트 (개념 모델) |
| Container | 할당 뷰타입 |
| Component | 런타임/모듈 뷰타입 |
| Code | 모듈 뷰타입 |

두 접근법의 차이: C4는 **문서화 구조**에 집중하고, 리스크 주도 접근법은 **리스크 완화**를 위해 뷰를 선택한다.
